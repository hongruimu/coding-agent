目前的不足
- 没有显式阶段：理解、计划、执行、评估都只靠 SYSTEM_PROMPT 约束，没有代码层面的状态。
- 没有进度事件：工具执行过程不会打印“正在读文件/正在运行测试”等过程信息。
- 没有风险控制：模型可以调用 run_command 执行任意 shell 命令。
- 没有变更审查：写文件后不会自动 git diff，模型不一定知道自己改了什么。
- 没有验证策略：是否运行测试完全靠模型自觉，没有代码强制。
- 超步处理较弱：达到 max_steps 后又允许模型继续拿到工具定义，但这最后一次不会执行工具调用。

记录下这一次工作的一些发现：
1、如果README.md已经相对很完整了，不会一直跑到max_steps，就直接return了
2、如果README.md不是很完整，会一直跑到5，跑到超过max_steps
3、没有将用户问题中的项目目录提取出来放到查找的workspace中，导致一直在Path.cwd()下找文件
4、在workspace下查找要读的文件和目录的时候，LLM产生的tool_calls中将要读的文件和目录未必是上一轮拿到的结果中所有的文件，而且先读哪些文件是不确定的，似乎和文件的层级深度有关，但是仍然不确切
5、max_steps的设置未必合理，因为LLM产生的too_calls的数量未必可控，会导致任务的执行未必彻底，会存在一些项目信息丢失的情况，导致README.md中的信息不完整
6、像这种总结整个工程，产生一份README.md文件，如果项目很大，是不可能把所有的文件都塞给LLM去理解的，现在的执行方式明显不合理，需要治理
7、LLM会自己产出一些tool_calls出来，比如这个例子的第5次执行是: `python -m compileall agent cli model tools`，这个就是用了我注册的run_command工具，但是为什么会执行这个python的命令，我并没有告诉它，不清楚是依据什么才决策要做这一步
8、在第4步就已经往README.md中写入文件了，但是是整个文件的写入，并没进行patch_replace，这个要解决
